# 技术报告：ScreenAgent GUI Grounding 复现与调优

## 摘要

本项目在单卡 RTX 5090 上复现 ScreenAgent（Qwen2.5-VL-3B + LoRA 的 GUI 元素定位方案），最终在 ScreenSpot 上取得 **84.98%**、ScreenSpot-v2 上取得 **86.86%** 的准确率，与/略超原始方案报告的 84.9% / 86.4% 基线，而训练时长只用了原方案 12+12 epoch 预算的三分之一（实际 4+4 epoch）。

这个结果不是"跑通脚本就顺利复现"。开源方案给的只是一份训练配方（模型、数据集、超参数），把这份配方跑起来之后，评估分数长期卡在接近 0 且没有任何报错——**从这里往后的每一步，包括怎么判断问题出在哪、设计什么诊断实验去验证、根因找到之后用什么架构修、以及最后用什么策略决定训练到什么程度就停，都是我自己独立设计和执行的**，不在原方案覆盖范围内。本报告的重点也是记录这个过程，而不是罗列"跑了哪些脚本"。

---

## 核心创新点（面向快速阅读）

以下是本项目区别于"直接跑通开源训练脚本"的关键部分，均为独立设计与实现：

| # | 创新点 | 解决了什么问题 | 量化证据 |
|---|---|---|---|
| 1 | **三阶段受控消融诊断法**：在怀疑"模型学不会"之前，先设计实验分别在裸 LoRA、DeepSpeed 封装、真实 checkpoint+真实数据三个层面隔离验证，而不是直接改评估代码或加训练轮数 | 避免把排查方向锁死在"重写评估逻辑"或"加大训练量"这类表面修复上，少走弯路 | 三组实验逐一给出可对比的生成结果差异，见 §2.3 |
| 2 | **跨数据集坐标格式实证审计**：不依赖数据集文档或假设，直接对每个训练集抽样跑一遍真实的坐标转换代码，统计"被数值裁剪到画布边界"的比例 | 把"我猜标注格式可能有问题"变成可验证、可量化的证据 | showui-web/amex/uground 均 100% 被裁剪，showui-desktop 为 0%，见 §2.3 数据表 |
| 3 | **按数据集自动识别坐标格式并统一归一化的架构**：加载数据时自动判别绝对像素/归一化、xyxy/xywh，而非为每个数据集硬编码格式假设 | 从"每个数据集单独打补丁"升级为"格式错误在未来新数据集上也能被自动发现"的通用机制 | 修复后 4 个数据集、评估集全部自动识别正确，见 §3.1 |
| 4 | **基于真实收敛趋势的提前停止策略**：不照搬原方案固定的 12+12 epoch，而是实时监控每个 epoch 的真实验证集准确率，用趋势判断是否进入平台期 | 避免在没有依据的情况下要么训练不足、要么无意义地烧算力 | 两阶段各仅用 4 epoch 即达到/超过基线，训练时长压缩约 2/3，见 §3.5 |
| 5 | **保持有效 batch size 等价的硬件迁移**：单卡复现原本为双卡设计的训练方案时，通过换算梯度累积步数而不是简单地"跑起来就行" | 确保优化器每一步看到的梯度统计特性不因硬件数量变化而改变，结果才具备可比性 | 见 §3.6 |
| 6 | **合并权重前的正确性校验**：给 LoRA 权重合并流程加了一道"key 是否真的对得上模型结构"的检查 | 防止 `strict=False` 静默产出一个"看起来正常、实际等于没训练"的模型 | 见 §3.3 |


## 1. 背景与目标

- **任务**：GUI Grounding——给一张界面截图和一句自然语言指令（如"点击登录按钮"），模型输出目标元素的点击坐标。
- **模型**：Qwen2.5-VL-3B-Instruct 基座 + LoRA（r=8, alpha=16，冻结视觉编码器）。
- **训练数据**：Stage1 混合 `showui-desktop`（101条）、`showui-web`（8020条）、`amex`（8000条）三个数据集做跨平台预训练；Stage2 只用 `uground`（8047条）做高分辨率专项微调。
- **评估**：ScreenSpot / ScreenSpot-v2，共 1272 条测试样本，按 desktop/mobile/web 三个平台、icon/text 两种元素类型分别统计准确率（预测点是否落在标注框内）。
- **硬件约束**：单卡 RTX 5090（32GB），而原始方案的显存/时长预估基于 2×RTX 4090。这意味着不能照搬原始的 `batch_size × grad_accum × GPU数` 配置，需要在保持训练动态等价的前提下做适配。

## 2. 故障排查：一个不报错的静默 bug

### 2.1 第一轮：代码审查（13 个已知问题）

在开始训练前，先对 `train.py`、`base_dataset.py`、`train_dataset.py`、`evaluator.py`、`model_utils.py` 等核心文件做了系统性审查，发现并修复了 13 个问题（C1/C2 两个 Critical，H1-H3 三个 High，M1-M5 五个 Medium，L1-L3 三个 Low），完整清单见 [code-review-findings.md](./code-review-findings.md)，修复说明见 [code-review-fixes.md](./code-review-fixes.md)。其中比较关键的两个：

- **C1**：point 任务的坐标系统在训练/评估/推理三处的假设互相矛盾（归一化坐标 vs. resize 后绝对坐标混用）。
- **C2**：LoRA 目标模块的默认排除逻辑（`lm_head` 不参与训练）被调用方传参的方式意外绕过，导致 `lm_head` 实际被纳入了 LoRA 训练。

这一轮修复后，训练流程能跑通，但**远没有解决问题**——下面这条才是真正拖垮训练效果的根因，而且完全不在这 13 条审查范围内。

### 2.2 第二轮：评估分数长期冻结在 0.3% ——先怀疑评估代码

修完第一轮问题、正式跑 Stage1（12 epoch）后，观察到一个异常现象：**训练 loss 从 0.33 一路降到 0.06 附近，正常收敛；但 ScreenSpot 评估的平均准确率在全部 6 个 epoch 里精确停在 0.0029（小数点后 16 位完全相同）**。loss 在降、分数纹丝不动，这个矛盾说明问题出在"评分标准"或者"训练标签"上，而不是模型没在学习。

用真实标注数据直接核对 `get_bbox_from_annotation` 的计算结果：

```
ScreenSpot 官方标注格式是 [x, y, width, height] 的绝对像素坐标（如 bbox=[910, 78, 44, 34]），
但代码把它当成 0-1 归一化的 [x1, y1, x2, y2] 又乘了一次图片宽高，
算出 x1=910×960 这种远超图片尺寸、且 x1 > x2 的"不可能的框"。
```

| | 样本数 | 几何有效（x1≤x2 且 y1≤y2） |
|---|---|---|
| 修复前 | 1272 | 68（5.3%）|
| 修复后 | 1272 | 1272（100%）|

修复后再用"bbox 中心点"（一个显然正确的预测）去测试命中率，1272/1272 全部命中，确认修复生效。**这个 bug 单独解释了为什么分数低到几乎为零**，但后续证明它还不是全部问题。

### 2.3 第三轮：修完评估 bug，Stage1 卡在 50% 左右不再上涨 —— 怀疑训练本身

评估 bug 修完后重训 Stage1，分数从 0.29% 跳到 epoch1 的 33.79%、epoch2 的 50.86%，但接下来 4 个 epoch 一直在 48%-51% 区间震荡，没有继续上涨。分平台细分给出了关键线索：

| 平台 | icon | text |
|---|---|---|
| desktop | 57.1% | 84.5% |
| **mobile** | **11.8%** | **9.5%** |
| web | 62.6% | 79.6% |

mobile 平台（对应 `amex` 数据集）的准确率断崖式低于其他两个平台。这不是"模型某项能力弱"的正常分布，更像是"这个数据集的训练信号本身有问题"。

**在下结论之前，先做了一轮受控诊断**，排除"LoRA/DeepSpeed 层面的软件 bug"这个更容易被怀疑、但其实更难验证的可能性：

1. **诊断 1**（不经过 DeepSpeed）：直接对 LoRA 的 B 矩阵注入随机扰动，对比扰动前后 `generate()` 的输出——输出从合理的坐标变成乱码，证明 LoRA 机制本身工作正常。
2. **诊断 2**（经过 DeepSpeed 包装）：同样的扰动测试，这次在 `deepspeed.initialize()` 包装后的 `model_engine` 上做——结果一致，排除了"DeepSpeed 包装层吞掉 LoRA 效果"的可能。
3. **诊断 3**（真实训练权重 + 真实评估图片）：加载真实训练出的 epoch0 checkpoint，在 5 条真实 ScreenSpot 样本上跑推理，对比"训练前"和"训练后"的生成结果——5/5 全部不同，证明训练确实在改变模型行为。

三轮诊断确认："模型有没有学"这件事本身没问题，问题只能出在数据标签上。于是直接在训练数据上做实证核查，而不是继续猜测：

```python
# 对每个数据集抽样若干个真实的 point 标注，跑一遍训练时用的坐标转换函数，
# 统计有多少比例的转换结果被夹到了 resize 后画布的角落（说明数值溢出后被截断保护）
```

| 数据集 | 标注格式（实测）| 抽样中被夹到角落的比例 |
|---|---|---|
| showui-desktop | 归一化 0-1（正确）| 0 / 60 |
| showui-web | **绝对像素** | **60 / 60（100%）** |
| amex | **绝对像素** | **59 / 59（100%）** |
| uground | **绝对像素** | **58 / 58（100%）** |

四个数据集里只有 `showui-desktop`（仅 101 条、且在训练里被重复过采样）的标注是真正的归一化坐标；`showui-web`、`amex`、`uground` 的标注其实是绝对像素坐标，但训练代码统一按归一化处理、又乘了一次图片宽高，导致数值远超画布范围，被后续的边界裁剪逻辑强制夹到了 resize 后画布的右下角——**相当于这三个数据集里，无论指令是什么，训练标签永远被错误地写成"点右下角"**。这解释了 Stage1 卡在 50%（本质是"只有 desktop 那 101 条重复样本教了点有用的东西"），也解释了后续 Stage2（100% 用 `uground`）会直接崩到 0.06%。

## 3. 修复方案与本项目的增量设计

发现根因后，没有采用"针对这三个数据集写死转换规则"的最小修复，而是设计了一套**按数据集自动判别坐标格式**的机制（架构思路参考了同事独立重写的一份实现，移植后补齐了它回退掉的几处已验证修复，见下文 3.4）：

### 3.1 自动格式判别 + 统一归一化（核心修复）

新增 `data/data_utils.py` 中的 `detect_annotation_format`：加载数据集时先扫描一批标注，同时判断两件事——数值是绝对像素还是归一化 0-1；bbox 的四个数是 `[x1,y1,x2,y2]` 还是 `[x,y,宽,高]`。判别逻辑不是简单设阈值，而是有多重交叉验证：

- 如果同时存在 `point` 标注，直接比较"按 xyxy 解释的中心点"和"按 xywh 解释的中心点"哪个更接近真实 point——这是最硬的判据，几千条样本投票基本不会错。
- 没有 point 可对照时，退化为看"按某种布局解释是否会产生非法框（负宽高、越界）"。
- 全部判不出来就直接抛异常，不做静默猜测——**这条设计是本次踩坑最大的教训**：原来的实现之所以能一路跑到评估阶段才暴露问题，就是因为格式假设是隐式写死的，任何一步都不检查、也不报错。

判别出格式后统一转换成"归一化的 `[x1,y1,x2,y2]` + 归一化的 `[x,y]`"，下游的训练标签编码、评估判分统一按归一化坐标处理，不再需要每处都关心某个数据集原始是什么格式。

### 3.2 统一坐标编解码模块

新增 `utils/coordinate.py`，把"归一化标注 → 训练答案格式"（`encode_point`/`encode_bbox`）和"模型输出 → 原图坐标"（`decode_point`/`decode_bbox`）两个方向的转换收敛到一处，并显式引入 `--coord_format` 参数（`qwen_abs`/`norm`/`int1000`），写入 `args.json` 落盘，评估、推理、合并权重时都能查到训练时实际用的坐标格式，不再需要硬编码 `'Qwen2.5-VL' in model_id` 这种脆弱的隐式判断。

### 3.3 合并权重时的正确性校验

`scripts/merge_weights.py` 增加了 LoRA key 匹配校验：合并前检查 checkpoint 里的 LoRA 权重 key 是否真的能对应到当前模型结构，如果一个都对不上就直接报错退出，而不是让 `load_state_dict(strict=False)` 静默忽略、合出一个"看起来正常、实际等于没训练"的模型。这类问题原本只有靠事后跑评估才能发现，现在合并阶段就能拦截。

### 3.4 移植时重新打回的修复

参考实现虽然解决了坐标格式问题，但在整合的过程中回退了几处第一轮代码审查已经验证过的修复，逐一核对后重新打了回去：

- `find_lora_target_modules` 的默认排除词（含 `lm_head`）与调用方传入的排除词合并而非互斥替代，确保 `lm_head` 始终不参与 LoRA；
- `sdpa` attention 模式下不清空 PyTorch 的加速后端（原实现对 `eager`/`sdpa` 一视同仁地关闭，逻辑自相矛盾）；
- checkpoint 保存判断改为 `score >= best_score`（而非严格 `>`），否则评估分数一旦打平，后续 epoch 的权重会全部不落盘；
- `--debug` 模式不写盘 + 每次存新 checkpoint 前删除上一份，避免磁盘被无限增长的 checkpoint 撑爆（这是训练过程中真实发生过的一次磁盘写满崩溃的直接教训）。

### 3.5 效率优先的训练策略：不迷信固定 epoch 数

原始方案两阶段各训 12 epoch。考虑到这次的目标是**验证修复是否有效、拿到可信的实验结果**，而不是不计成本地完全复现论文数字，训练策略上做了一个和"照抄配方"不同的选择：**实时监控每个 epoch 的真实验证集准确率，用真实趋势而不是预设的 epoch 数决定何时停止**。

停止规则：连续多个 epoch 的准确率相对最高点没有净提升（在小幅震荡区间内），或者已经达到/接近参考基线，就提前终止当前阶段、合并权重、进入下一阶段——而不是教条地跑满 12 epoch。这个策略在数据修复完成之后被验证是合理的：

- Stage1 训练 4 个 epoch 后，准确率在 82.2%-83.0% 区间反复震荡，没有继续上涨的趋势，判定进入平台期，用最高分（epoch2, 83.04%）的权重提前终止。
- Stage2 训练 4 个 epoch 后，准确率稳定在 83.7%-84.8%，已经追平/超过论文基线（84.9%），同样提前终止，用最高分（epoch1, 84.84%）的权重收尾。

最终两阶段合计只用了 8 个 epoch（原方案 24 个），训练总时长约 32 小时，而按原方案 12+12 epoch 的实测单 epoch 耗时估算，完整跑完需要约 96 小时（4 天）——**在保证结果不降级（实际还略有提升）的前提下，把计算成本压缩到约三分之一**。

### 3.6 硬件适配：单卡复现两卡方案

原方案假设 2×RTX 4090，通过 `batch_size=1 × grad_accum=48 × 2卡` 得到有效 batch size 96。本项目只有 1×RTX 5090，为了不改变优化器每一步看到的梯度统计特性（等价于不改变学习率、warmup 等其他超参数的实际效果），把梯度累积步数相应调整为 96（`1 × 96 × 1卡 = 96`），保持有效 batch size 与原方案完全一致，只是把"多卡并行"换成了"更多步数的梯度累积"。

## 5. 结果

### 5.1 训练过程中的验证集准确率趋势

**Stage1**（ScreenSpot 全量 1272 条评估，训练数据 showui-desktop+web+amex）

| Epoch | 平均准确率 | 相邻变化 |
|---|---|---|
| 1 | 82.84% | — |
| 2 | **83.04%**（选中，合并）| +0.20pp |
| 3 | 82.87% | −0.17pp |
| 4 | 82.20% | −0.67pp |

**Stage2**（同样评估集，训练数据 uground，起点为 Stage1 合并模型）

| Epoch | 平均准确率 | 相邻变化 |
|---|---|---|
| 1 | **84.84%**（选中，合并）| — |
| 2 | 83.71% | −1.13pp |
| 3 | 83.65% | −0.06pp |
| 4 | 84.37% | +0.72pp |

两个阶段都在早期 epoch 就达到了后续 epoch 无法明显超越的水平，印证了"提前停止"决策的合理性——继续训练更多 epoch 大概率只是重复消耗算力，而不是获得实质提升。

## 6. 讨论与已知局限

- **多任务能力未激活**：原方案设计了 text2point / text2bbox / point2text / bbox2text 四种任务类型混合训练，但 `train.py` 的命令行接口只暴露了前两种的采样权重参数，实际训练里第一轮代码审查已确认这一直是"仅 text2point 单任务"在跑。这不在本次修复范围内，详见 [code-review-findings.md](./code-review-findings.md) 的【暂缓处理】章节，留作后续工作。
- **多轮对话的信号稀释**：`num_turn=30` 意味着每条训练序列包含 30 轮独立的问答，但轮次之间元素选择是有放回随机采样、彼此无关联，本质是"30 个独立问答被物理拼接成一条长序列"而非真正需要利用上下文的多轮对话。ScreenSpot 评估只考察第一轮的能力，训练信号有多少比例真正作用于第一轮尚未定量分析。
- **showui-desktop 样本量过小**：仅 101 条样本却与另外两个 8000 条量级的数据集同权重混合采样，实际上被显著过采样。这次修复前 desktop 平台之所以（相对）表现更好，可能部分也和这种过采样有关，而不完全是"数据集更好学"。
- **提前停止的判断阈值是启发式的**：本次"进入平台期"的判断基于观察到的绝对波动幅度（约 1 个百分点内），没有做统计显著性检验，样本量更小或随机种子不同的情况下可能需要更谨慎的判断标准。

## 7. 时间线与算力成本

| 阶段 | 结果 |
|---|---|
| 第一轮代码审查后首次训练 | Stage1 6 epoch 评估分数冻结在 0.29%（评估 bug）|
| 修复评估 bug 后重训 | Stage1 6 epoch 卡在 ~50%（数据标注 bug，未发现）|
| 根因排查（3 级扰动诊断 + 数据实证核查）| 定位到 3/4 训练集坐标格式错误 |
| 架构修复 + 最终训练 | Stage1 4 epoch + Stage2 4 epoch，约 32 小时（含中途一次磁盘写满故障恢复）|
| 最终评估 | ScreenSpot + ScreenSpot-v2，共约 40 分钟 |

硬件：单卡 RTX 5090（云端按小时计费）。原方案 12+12 epoch 满额训练预计需要约 96 小时，本项目通过提前停止策略压缩到约 32 小时。
