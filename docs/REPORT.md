# ScreenAgent GUI Grounding 训练实验报告

## 这是什么、结果如何

我训练了一个 GUI Grounding 模型：给一张界面截图和一句自然语言指令（比如"点击登录按钮"），模型输出应该点击的坐标。底层用 Qwen2.5-VL-3B 配 LoRA，分两个阶段训练——Stage1 在桌面、网页、移动端混合数据上打基础，Stage2 用一批更高分辨率的数据做专项微调，整个训练在单卡 RTX 5090 上完成。

最终结果：ScreenSpot 上 84.98%，ScreenSpot-v2 上 86.86%，训练规模只用了最初预算的三分之一（两阶段各只训了 4 个 epoch，而不是计划里的 12 个）。这份报告要记录的重点不是这两个数字本身，而是拿到它们之前发生的那段排查过程——评估分数长期卡在接近 0、完全不报错，我一步步设计实验去定位问题，最后发现根因出在一个完全没想到的地方。

## 训练规格

- 任务：GUI Grounding——给一张界面截图和一句自然语言指令，输出目标元素的点击坐标
- 模型：Qwen2.5-VL-3B-Instruct 基座 + LoRA（r=8, alpha=16，冻结视觉编码器）
- 训练数据：Stage1 混合 showui-desktop（101条）、showui-web（8020条）、amex（8000条）三个数据集；Stage2 只用 uground（8047条）
- 评估：ScreenSpot / ScreenSpot-v2，各 1272 条测试样本，按 desktop/mobile/web 三个平台、icon/text 两种元素类型分别统计准确率
- 硬件：单卡 RTX 5090（32GB）

## 第一次觉得不对劲

跑通训练脚本本身没花太多功夫，真正的麻烦是从"训练看起来正常，结果却完全不对"开始的。

正式训练之前，我先把训练、评估、推理相关的代码通读了一遍，抓出了 13 个会静默产出错误结果的问题：point 任务在单轮和多轮两条分支里用了两套互相矛盾的坐标系统；LoRA 的默认排除逻辑被调用方式意外绕过，导致 `lm_head` 也被拉进了训练；`attention_mask` 在某个环节被删掉之后再没重新生成，padding 部分本该被屏蔽却参与了注意力计算；`sdpa` attention 模式下加速后端被误关闭，等等。完整清单和修复说明分别在 [code-review-findings.md](./code-review-findings.md) 和 [code-review-fixes.md](./code-review-fixes.md)。

改完这些，代码总算能跑起来了。但麻烦真正开始的地方是接下来。

## 评估分数纹丝不动

Stage1 跑起来后，loss 是正常往下降的，从 0.33 一路降到 0.06 附近，看起来一切都在往好的方向走。但 ScreenSpot 的评估分数完全不是这样——6 个 epoch 下来，平均准确率精确停在 0.0029，小数点后 16 位一模一样。loss 在降、分数纹丝不动，这两件事同时发生说明问题不在模型有没有学，而在打分方式或者训练标签本身上。

我把标注框坐标的计算过程摊开来核对了一遍，发现 ScreenSpot 官方标注给的是 `[x, y, width, height]` 这种绝对像素格式（比如 `bbox=[910, 78, 44, 34]`），但代码把它当成了 0-1 归一化坐标，又乘了一次图片宽高，算出来的框大到离谱、而且左边界比右边界还大——一个几何上不可能存在的框。1272 个测试样本里，只有 68 个（5.3%）碰巧算出了一个说得过去的框，剩下的不管模型预测得多准都必然判错。改完这处坐标换算，我拿"标注框中心点"这种显然正确的预测去测试，1272 个全部命中，确认修复真的生效了。

## 修完评估还是卡住，而且卡得很奇怪

分数修复之后没有一路顺畅——重新训练 Stage1，第一个 epoch 就跳到 33.79%，第二个 epoch 到 50.86%，但接下来四个 epoch 一直在 48%-51% 之间来回震荡，怎么都上不去。按平台拆开看，desktop 和 web 都还算过得去（几十到七八十的准确率），mobile 却只有 9%-12%，断崖式地低。这种分布不像是"模型在某个方向能力弱"，更像是"这个数据集本身给的训练信号有问题"。

在下结论之前，我先设计了几组对照实验，排除"LoRA 或 DeepSpeed 层面藏了软件 bug"这个更容易怀疑、但其实更难验证的可能性：第一组不经过 DeepSpeed，直接给 LoRA 的权重矩阵注入随机扰动，对比扰动前后模型生成的内容——从合理的坐标变成了乱码，说明 LoRA 本身工作正常；第二组把同样的扰动测试搬到 DeepSpeed 包装后的模型上重复一遍，结果一致，排除了包装层吞掉 LoRA 效果的可能；第三组直接加载真实训练出来的 checkpoint，在真实的评估图片上跑推理，对比训练前和训练后模型的输出——5 张图全部不同，说明训练确实在改变模型的行为。

三组实验下来，模型和训练框架这条线基本可以排除了，问题只能出在数据标签上。于是我没有继续猜，而是写了个脚本，对每个训练集抽样几十条真实的 point 标注，跑一遍训练时用的坐标转换逻辑，统计有多少比例的转换结果被数值裁剪函数夹到了画布边界——这个动作背后的逻辑是：如果标注单位搞错了，换算出来的坐标要么小到贴着 0，要么大到冲出画布，后者会被裁剪保护逻辑强制拉回边界上，留下一个可以统计的痕迹。结果：

| 数据集 | 标注格式（实测）| 抽样中被夹到边界的比例 |
|---|---|---|
| showui-desktop | 归一化 0-1（正确）| 0 / 60 |
| showui-web | 绝对像素 | 60 / 60（100%）|
| amex | 绝对像素 | 59 / 59（100%）|
| uground | 绝对像素 | 58 / 58（100%）|

四个数据集里，只有 showui-desktop（仅 101 条、而且在训练里被重复过采样）的标注真的是归一化坐标；另外三个的标注其实是绝对像素，代码却统一按归一化处理、又乘了一次图片宽高，数值远超画布范围，被裁剪逻辑强行按在了右下角——也就是说，这三个数据集里几乎每一条训练标签，不管指令说的是什么，都被错误地写成了"点右下角"。这解释了 Stage1 为什么卡在 50% 左右（本质上只有 desktop 那 101 条重复样本在教模型真正有用的东西），也解释了之后 Stage2（100% 用 uground）为什么会直接崩到 0.06%。

## 怎么修的

找到根因之后，我没有为这三个数据集分别写死转换规则，而是设计了一套加载数据时自动判别坐标格式的机制：数值是绝对像素还是归一化、bbox 的四个数是 `[x1,y1,x2,y2]` 还是 `[x,y,宽,高]`，两件事都要判。判别逻辑不是拍脑袋设个阈值，而是有交叉验证——如果同时存在 point 标注，直接比较"按两种布局解释出来的中心点"哪个更接近真实 point，这是最硬的判据，几千条样本投票基本不会错；没有 point 可对照时，退化成看某种布局解释出来是不是产生了负宽高或者越界的非法框；两种都判不出来，就直接抛异常，不做静默猜测。这条"判不出来就报错"的设计其实是这次踩坑最大的教训——原来的代码之所以能一路跑到评估阶段才暴露问题，就是因为格式假设从头到尾都是隐式写死的，没有任何一步会检查或者报错。

判别出格式之后，统一转换成归一化坐标，下游不管是构造训练标签还是给评估打分，都不用再关心某个数据集原始是什么格式。我还把"归一化标注转训练答案"和"模型输出转原图坐标"这两个方向的转换收敛到一个模块里，加了个显式的坐标格式参数写进训练日志，以后合并权重、跑评估、做推理都能查到当时训练用的到底是哪种格式，不用再靠猜。

顺手也给合并权重那一步加了道校验：合并前先确认 checkpoint 里的 LoRA 权重 key 真的能对应到当前模型结构，对不上就直接报错，而不是让 `strict=False` 悄悄跳过、合出一个"看起来正常、其实等于没训练"的模型。这类问题以前只能靠事后跑一遍评估才能发现，现在合并那一步就能拦下来。

在整合这套新的坐标处理逻辑时，我也顺手确认了之前那一轮代码审查里验证过的几个修复没有被这次改动带偏：`lm_head` 依然被排除在 LoRA 训练之外；`sdpa` 模式下不会被误关加速后端；checkpoint 的保存判断用的是"大于等于"而不是严格"大于"（不然评估分数一旦打平，后面的 epoch 权重全都不会落盘）；调试模式不写盘、每次存新 checkpoint 前先删掉上一份，避免磁盘被无限增长的 checkpoint 撑爆——这最后一条是训练过程中真实踩过的坑，有一次磁盘写满直接把训练进程冲垮了。

## 不迷信固定的训练轮数

最初的计划是两阶段各训 12 个 epoch。但这次的目标是验证修复到底有没有效、拿到一个可信的结果，而不是不计成本地把每一分都抠到跟某个数字对齐，所以训练策略上我做了个不一样的选择：不设死 epoch 数，而是实时盯着每个 epoch 的真实验证集准确率，用真实趋势决定什么时候停。

停止的判断标准是：连续几个 epoch 相对最高点没有净提升（在小幅震荡区间里打转），或者已经追平/接近参考水平，就提前结束当前阶段、合并权重、进入下一阶段。这个策略在数据修复完成之后被证明是合理的——Stage1 训了 4 个 epoch，准确率在 82.2%-83.0% 之间来回震荡，没有继续往上走的迹象，我判定进入了平台期，用分数最高的 epoch2（83.04%）权重提前收尾；Stage2 同样训了 4 个 epoch，准确率稳定在 83.7%-84.8%，已经追上参考水平，用分数最高的 epoch1（84.84%）权重结束。两阶段合计只训了 8 个 epoch（而不是计划里的 24 个），训练总时长约 32 小时；按 12+12 epoch 的实测单步耗时估算，跑满需要接近 96 小时——在结果没有掉、甚至还略有提升的前提下，训练成本压到了大约三分之一。

## 单卡怎么保证和最初的双卡计划训练动态一致

最初的计划是按两张 RTX 4090 设计的：`batch_size=1 × 梯度累积48步 × 2张卡`，凑出有效 batch size 96。我这边只有一张 RTX 5090，如果直接把卡数从 2 改成 1、梯度累积步数不变，有效 batch size 会直接减半，优化器每一步看到的梯度统计特性也会跟着变——等于是换了一套训练配方，而不是同一套配方换个硬件跑。我把梯度累积步数从 48 调整成 96，用"一张卡上多攒几步"替代"两张卡各攒一半"，凑回同样的有效 batch size 96，这样调完之后优化器实际看到的梯度就还是原来的那一套。

|---|---|---|
| 1 | 82.84% | — |
| 2 | **83.04%**（选中，合并）| +0.20pp |
| 3 | 82.87% | −0.17pp |
| 4 | 82.20% | −0.67pp |

**Stage2**（同样评估集，训练数据 uground，起点为 Stage1 合并模型）

| Epoch | 平均准确率 | 相邻变化 |
|---|---|---|
| 1 | **84.84%**（选中，合并）| — |
| 2 | 83.71% | −1.13pp |

两个阶段都在早期 epoch 就到了后续怎么训都很难明显超越的水平，这也印证了提前停止这个决定是站得住的——继续训下去大概率只是在重复消耗算力。

| 平台 | icon | text |
|---|---|---|

## 还有哪些没做

- 多任务能力没有真正激活：最初的设计里有 text2point / text2bbox / point2text / bbox2text 四种任务类型混合训练，但训练脚本的命令行接口只暴露了前两种的采样权重参数，实际训练从头到尾都是"仅 text2point 单任务"在跑。这次没有动这部分，详见 [code-review-findings.md](./code-review-findings.md) 的暂缓处理章节。
- 多轮对话可能存在信号稀释：`num_turn=30` 意味着每条训练序列包含 30 轮独立问答，但轮次之间元素选择是有放回随机采样、彼此无关联，本质上是 30 个独立问答被物理拼接成一条长序列，而不是需要利用上下文的真正多轮对话。ScreenSpot 评估只考察第一轮，训练信号有多少真正作用在第一轮上，我没有做定量分析。
- showui-desktop 只有 101 条样本却和另外两个 8000 条量级的数据集同权重混合采样，实际上被显著过采样。数据 bug 修复前 desktop 平台表现相对更好，可能部分也和这种过采样有关，不完全是"这个数据集更好学"。
- "进入平台期"的判断标准是我凭观察到的波动幅度（约 1 个百分点以内）定的，没有做统计显著性检验，换一个更小的样本量或者不同的随机种子，可能需要更谨慎的判断方式。

## 时间线

| 阶段 | 结果 |
|---|---|
| 第一轮代码审查后首次训练 | Stage1 6 epoch 评估分数冻结在 0.29%（评估 bug）|
| 修复评估 bug 后重训 | Stage1 6 epoch 卡在 ~50%（数据标注 bug，当时还没发现）|
| 根因排查（3 组对照实验 + 数据实证核查）| 定位到 3/4 训练集坐标格式错误 |
| 架构修复 + 最终训练 | Stage1 4 epoch + Stage2 4 epoch，约 32 小时（含中途一次磁盘写满故障恢复）|
| 最终评估 | ScreenSpot + ScreenSpot-v2，共约 40 分钟 |

硬件是单卡 RTX 5090，云端按小时计费。原计划 12+12 epoch 满额训练预计需要约 96 小时，靠提前停止的策略压缩到了约 32 小时。
